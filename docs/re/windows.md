# Text windows and limits

The width gate for phase 6. `tbl/limits.tsv` holds one row per string, generated by `tools/debug/limits.py` from a marker tour; `tools/lint.py` enforces it. Check one line while writing it:

    python -X utf8 tools/lint.py --fit "Hello there!{nl}Second line.{end:00}" m123

Limits are in 8 px cells, because the engine lays out cells. English averages about 6.3 px a character including spaces (`tbl/vwf_font.txt`), so 16 cols is about 20 characters.

## Rules the game imposes
All **verified** by disassembly of 0x8038660 and 0x80389C8, and each seen in a stress tour.
- **A `{page}` costs a column.** The measure routine counts the page break as a cell on its line, so in bubbles and signs a line ending in `{page}` has one cell less. A 14-cell sign line before `{page}` measured 15, went over budget and showed "ERROR". The box has no measure routine, so this doesn't apply there.
- **Sprite slots.** One sprite per cell, from slot `+0x30 + +0x2A`, and 128 slots exist: `+0x30 + +0x2A + even(cols) * rows` must stay at or under 128 or the game swaps the text for "ERROR". Base is 63 in talk scenes (65 cells), 87 in stage scripts (41 cells), 100 on signs (28 cells). `+0x2A` grows by `even(cols) * rows` for each bubble already open.
- **Tile room.** Cells take 2 OBJ tiles each from tile `+0x34 + +0x26 * 2`. Base tile is 160 in most talk scenes, 896 in stage scripts, 64 on signs. `+0x26` grows by `rows * cols + last line's cells` for each bubble already open, which is **one row more than the bubble shows**. Cells stay in VRAM after the bubble closes, so a cell past the scene's next OBJ tile paints over an actor for the rest of the scene. Seen in `talk10`: a second bubble landed on tiles 288-320 and turned an actor into a black block with text in it. `tile_cells` in `tbl/limits.tsv` is the room up to the scene's next OBJ tile, from the `oam` lines of `tools/debug/bublog.lua`.
- Bubble strings stay under 255 bytes (string index +0x21 is a byte), and any string under 253 different cells.
- Rows: never more than 3 in the Japanese. Nothing was tested past 16 x 3.

## How the numbers were made
1. `tools/debug/marker.py --bubble 0`: every string at its Japanese size. Tour: positions and tiles. `tools/debug/limits.py` turns them into limits: `(min(x, 240 - x) - 8) / 4` cols, rounded down to even and capped at 16; `(min(y, 160 - y) - 8) / 8` rows, capped at 3. A string keeps at least its Japanese size, which overflows no worse than the original.
2. `tools/debug/marker.py --limits`: every string filled to its limit. Tour `work/qa/mk_L` (2026-11-07): 160/160 scenes, no bubble fell back to "ERROR" (`markercover.py` found no pointer outside the id list), no clipped bubble in the shots read. Two at-limit strings did not appear at all: s008 and s029 came to 292 bytes (10 pages), over the 254-byte limit. So that limit is real, and `lint.py` enforces it: long signs must average about 25 bytes a page.
3. Glyph torture line (`torture.gba`, `work/qa/torture_t2/zoom.png`): all printable ASCII plus a double space in the box, every glyph and width correct.

## Overrides
`tbl/limits_override.tsv` sits on top of the generated `limits.tsv` (`tools/lint.py`), with a reason per row:
- m034, m159, m173, m183 go past their measured width. They sit at x 194-200, but `KEEP_ON_SCREEN` in `tools/build.py` pulls them in: logged x 184 at 12 cols for m159 and m173, x 192 at 10 for m034 and m183. A fresh tour of the build would measure this and make the rows unnecessary.

**Keep-on-screen argument.** `AF slot a b c anim text`: b is 0 in all 715 Japanese AF ops. Nonzero, the game pulls the bubble in until its frame fits. Values 1, 184 and -16 all gave the same x, so it acts as a flag, not a position. **verified** from bubble logs in `fight4`, `fight5`, `defeat0`, `defeat4` and `win5` with the player moved up to 100 px left and 90 px right: no frame past either edge. At +90 all 56 boss lines showed and 45 sat exactly on the right edge. At -100, 24 sat on the left edge, and the run only reached m246 by frame 14000, so m247-m261 were not seen that far left. Only these 60 lines set it. **guess:** why the game has it, and which code reads it; the handler at 0x8057284 only stores it at +4.

## Limits of the measurement
- **Guessed rows** (`source` = guess in `tbl/limits.tsv`): s040 (empty) and the 39 pointerless strings.
- **Boss 5's defeat (m206-m261) follows the player.** The `win5`, `win5l` and `win5r` scenes run the fight, then force the boss's own defeat states from state 33 (object slot 33, call at 0x805B23A), with the player where the fight left him, 60 px left, or 40 px right. All 56 lines show, in the real rooms and through op 9B. Nearly every x moves 1:1 with the player, and the script never walks him to a set spot, so their room depends on where the player stood when the boss died. **limits.py** takes the tightest x of the three runs, so a line fits with the player at about x 60-160. Past that the keep-on-screen argument below holds the frame on screen, in place of clipping as the Japanese does. A real win by hand was not played: the forced state skips only the fight itself.
- **An actor can cover a bubble.** In `fight4` an orange sprite sits over the top-right bubble's right end at about x 220, y 30. The original ROM shows it too, so it is not a build bug; a line may lose a letter under it, as the Japanese does.
- **Defeat lines are measured with a swapped script** (`defeat*` scenes, `swap` in `tools/debug/warp.lua`), which skips ops that wait on a boss state. Actors may stand somewhere else in a real win, and bubbles that follow an actor move with it. m152-m182 sit near the top or bottom edge there; the Japanese does too at those positions.
- Bubbles following an actor were only logged where the mashed tour took that actor.
